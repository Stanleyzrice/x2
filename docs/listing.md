# 上品（草稿）

读者是推进上品的人和 agent。这份讲一个货源怎样变成一家店在售的商品：每一步怎样算做完、谁做、收件箱里写什么。x2 怎么一轮一轮推进在 [loop.md](loop.md)，每个词的意思在 [glossary.md](glossary.md)。

来源：lilto 旧工作台跑通过的单品建品（快照 `1c8a7926` 的 `legacy/`：2026-09-01 卖家中心的成功样本照抄，9-09、9-11 在真站上架过）。批量上传那条路不用：要等次日才能上架，图要等 Shopee 自己去拉。

## 怎样工作

**一个货源 × 一家店 = 一份商品稿。** 两家店各卖各的。x2 把能自动做的都做了（读货源、类目属性、规格和价格、图），agent 写文案，人在 NocoDB 里审稿、在收件箱里批准，`x2 run` 建商品、读回来核对、上架。

```
要上的货源 → x2 做商品稿 → agent 写文案 → 检查、台湾审核 → 人审稿、批准 → 建商品（下架）→ 读回来核对 → 上架 → 读回来
```

上哪些货源：现在是人贴链接；以后 agent 按策略自己选、自己做实验（见「策略」）。

## 每一步怎样算做完

| 一步 | 怎样算做完 | 谁 | 收件箱 / agent 要做的 |
|---|---|---|---|
| 要上的货源 | 「商品稿」里有这一行：哪家店、哪个货源、哪个策略 | 人贴链接（NocoDB 表单，或在终端里说）；以后 agent | — |
| 读货源 | 存下货源快照：规格（名字、价格、库存、重量）、主图、规格图、详情图、服务（一件代发、包邮、48 小时发货）、起订量 | x2 | agent：做商品稿 |
| 类目 | Shopee 推荐的叶子类目（标题加一张已传的图），在本店允许的类目里；出货天数取这个类目的上限 | x2；不在范围的给人 | 类目：不在本店范围 |
| 属性 | 类目的必填属性都有值，值一字不差取自属性树 | x2 按规则挑；要填字的给人 | 属性：要人填 |
| 重量 | 每个规格有重量（1688 的运费重量） | x2；1688 没给的人填 | 重量：要人填 |
| 国内运费 | 货源有包邮算 0；没有的人填，不当 0 | x2；人 | 国内运费：要人填 |
| 规格和价格 | 1688 的规格排成 Shopee 的规格（最多两层、最多 50 个、最高价不超过最低价 5 倍），每个规格按店铺设置核价 | x2 | — |
| 图 | 主图、详情图、规格图都过了筛字、译图、水印、看成品，传到 Shopee 有图片 id；要尺码表的类目有核过的尺码表 | x2（译图收费，记成写入） | 图：写出哪张、什么问题 |
| 文案 | 繁体标题 10–60 字、描述 3–3000 字，照「文案」的规矩 | agent | agent：写文案 |
| 检查 | 商品稿检查全过；Gemini 的台湾成品审核没挑出简体字、错字、误译 | x2 | 写出问题 |
| 审稿、批准 | 人在 NocoDB「商品稿」里看过（可以改字、改价、删图），在收件箱勾「批准」 | 人 | 批准：上架 N 个商品稿 |
| 建商品 | Shopee 上有这个商品（下架），读回来和提交的一致 | `x2 run` | — |
| 上架 | 在售，读回来一致 | `x2 run`（同一批，读回来对上了就接着上架） | — |

做完 = 这份商品稿在售。人改了批准过的商品稿：那一批不做，重新批准。

## 规格

照 lilto 的 `shopee_listing.py`：

- 规格名、选项名先转成台湾繁体（OpenCC s2twp）。
- 只保留各规格之间取值不同的那几层。两层而且是完整的组合（每个颜色都有每个尺寸）才保留两层，否则合成一层「款式」，值用空格连起来。
- 层名最多 14 字、选项名最多 20 字，重名的加「-2」「-3」。尺寸类的层只留字母码（S、M、L、XL、2XL……），别把「【M碼】」的括号连码一起洗掉。
- 规格图只挂在第一层的选项上（`value_list[].image_id`）；同一选项下规格图不一样就报错。
- 每个规格的货号 `sku` = `LT<货源 id>-<1688 规格 id>`（最多 40 字），订单靠它连回 1688 的规格。
- 只有一个规格的商品：单层、空名字（9-01 的成功样本）。
- 1688 没库存的规格不上。

## 核价

每个规格一个售价：满足「毛利率 ≥ 目标」和「毛利 ≥ 最低额」的最小整数售价（新台币），二分找。没有倍率、没有尾数 9、不按知虾的市场价夹。参数都在「店铺设置」里，一家店一行。

```
运费（元）= 重量（按 0.01 kg 取整）× 每公斤运费 + 贴单费
到岸成本（台币）=（1688 价 + 国内运费 + 运费）× 汇率
平台进账 = 售价 − 成交手续费 − 预售服务费 − 金流费 − 虾币回馈 − 免运方案费（各自四舍五入；免运方案费有每单最低）+ 运费净额
毛利 = 平台进账 − 到岸成本 − 售价 × 退货损耗
毛利率 = 毛利 ÷ 平台进账
```

| 参数 | ni1206 | cheeroutdoor | 来源 |
|---|---|---|---|
| 汇率（台币 / 元） | 4.4 | 4.4 | lilto `landed-cost.json`（2026-09-02 依账单和结算截图定） |
| 每公斤运费（元） | 10.8 | 10.8 | 海快直发 |
| 贴单费（元 / 单） | 1.5 | 1.5 | |
| 退货损耗（按售价） | 3% | 3% | |
| 最低毛利率（按进账） | 25% | 25% | |
| 最低毛利（元） | 8 | 8 | |
| 成交手续费 | 6% | 6% | |
| 预售服务费 | 3% | 3% | |
| 金流费 | 2.5% | 2.5% | |
| 虾币回馈 | 0 | 1.5% | |
| 免运方案费 | 6%，每单最低 NT$60 | 6% | |

lilto 拿这套算过真站：cheeroutdoor 的雨衣（1688 价 ¥19.9、1.6 kg）算出 NT$295，就是在售价。建商品前用现在的参数再核一次：改了汇率、费率，旧的商品稿会被挡下来重算。

## 图

```
原图 → 筛字（Gemini）→ d 删；m 送象寄译成繁体；p、n 照用；r 再问一次有没有后加的简体字
     → 本店水印（浏览器里画）→ 看成品（Gemini：水印看得见、没有供应商痕迹、看得清）→ 传 Shopee → 图片 id
```

- 一张图的身份是字节的 sha256：1688 的地址带缓存参数，按地址认会重复付钱。
- 1×1 的占位图、太小的图先按尺寸剔掉（AI 看不出来）。详情图宽 ≥ 700、高 ≥ 32；主图最多 9 张，第一张是封面；详情图最多 12 张。
- 象寄：一批最多 5 张，交一次收一次钱（约 0.025 元一张）。记成写入「译图」（不用批准）：先记意图再交；象寄说没译成的可以再交；没拿到答复的结果未知，不重交，收件箱请人核对。译好的图字节存进库（象寄的地址大约 80 天失效）。p 类（产品本体上的字）不送：象寄会把表盘、铭牌涂坏。
- 水印：每家店一套（文字、大小、不透明度、位置），从原图或译图开始画，不叠。两家店的封面因此不一样（Shopee 3.1.5：跨店标题和封面一样会禁卖）。字加一圈浅色描边：lilto 的深色字在深色图上看不见，整个商品卡住过。
- 尺码表：要尺码表的类目（或规格是 S/M/L 这类字母码）从详情图里找供应商的尺码表，Gemini 对比原图和译图：数值、单位都保留了才用；不加水印。
- 台湾成品审核：建商品前 Gemini 一次看 4 张成品，加标题、描述、规格，挑简体字、错字、误译；挑出任何问题就挡下。

## 文案

agent 写，照 lilto 的提示：

- 只用货源给的事实。标题核心品名放最前：「核心品名＋关键差异＋用途场景＋款式选择」，资料够时 55–60 字，最多 60 字（含空格）。
- 去掉厂家、批发、代发、冲量、定制、爆款这类采购端和卖家话术；不编造热销、现货、免运、品牌、认证、材质、功能、赠品、产地、疗效、发货时效。
- 描述按「商品介绍、规格选择、使用提醒」分段，最多 3000 字；不写价格；随机款要写明随机；不把不同规格的属性写成每件都有。
- 两家店各写各的，标题不能一样。

## 建商品、上架

- 在卖家中心的页面里发 `create_product_info`（从别处发会被反爬拒，90309999）。`product_info` 照 9-01 的成功样本逐字段照抄（`src/listing/product.ts`）。物流渠道数组照样本原样：有尺寸的渠道 `sizeid` 是 1，填错回 1000100256。
- 先建成下架（`unlisted: true`），读回来逐项核对（标题、货号、类目、重量、主图、尺码表、出货天数、物流、描述里的字和图、每个规格的选项、价格、库存），对上了才上架（`unlisted: false`），在在售列表里按货号找到、再核对一次。对不上就停在下架，给人看。
- 1000100256 是字段校验失败，不是重复：读响应 `msg` 里全部的 `Rule Type`（缺必填属性、详情图尺寸、缺尺码表……）写进写入的「原因」。
- 建商品结果未知（没拿到答复、成功了但没有商品 id）：不重发，按货号在全部商品里找；找不到请人到卖家中心看。
- 店铺被限制（页面跳到「權限不足 / 賣場遷移中」）：停下，收件箱请人处理；人可以在店铺设置里写「暂停上品」。

第一次建商品、上架要和人约好一个货源，`x2 run --try 建商品` 一起跑，跑完在卖家中心看一眼。

## 表

| 表 | 一行是 | 主要的列 | 为什么存 |
|---|---|---|---|
| 店铺设置 `shop_settings` | 一家店 | 核价参数（上面那张表）；上品的默认值：预售、起购量、库存上限、开哪些物流渠道；允许的类目；水印；暂停上品（写原因） | 人定的设置。在 NocoDB 里改；库里有范围约束（比例在 0–1、汇率大于 0），填错存不进 |
| 商品稿 `listings` | 一个货源 × 一家店 | 店、货源、策略；货源快照；类目、属性、出货天数；规格和价格（每个规格：货号、选项、成本、重量、售价、库存、图）；图（每张：原图、成品、图片 id、检查结果）；标题、描述；人填的（重量、国内运费、不上了、备注）；检查算出来的（卡在哪一步、问题、台湾审核）；建好以后的商品 id | 人的决定和审稿；建商品要的完整内容；核价用的参数快照 |
| 图 `images` | 一张图（字节的 sha256） | 从哪来（1688 地址、译自哪张）、宽高、筛字结果；译图的字节（付过钱，象寄的地址会失效）；每家店传上去的图片 id | 不重复付钱、不重复传 |

收件箱的 key：`listing-weight:<商品稿 id>`、`listing-freight:<id>`、`listing-category:<id>`、`listing-attr:<id>`、`listing-image:<id>`、`listing-audit:<id>`；批准还是 `approve:<批次>`。写入的防重复 key：`xiangji:<图的 sha256…>`、`create:<店>:<货号>`、`live:<店>:<货号>`。

NocoDB：「商品稿」放在侧栏「订单」下面，视图「要我看的」（等批准的，画廊：封面、标题、价格）、「卡住的」（按卡在哪一步分列的看板）、「全部」；「店铺设置」放在「订单设置」旁边。图传成附件给人看：要 `.env` 里有 NocoDB 的地址和账号。

## 策略（以后）

选品以后交给 agent 自己定策略、做实验，走 explore 和 exploit：

- 每份商品稿记下它从哪个策略来（现在都是「人选」）。
- 以后加一张「策略」表：押的是什么（假设）、怎么选、状态（试验中、在用、停了）。
- 按策略看效果：它上出来的商品的曝光、点击、加购、订单、毛利（Shopee 的商品表现现读，`x2 shopee performance`），agent 据此多用好的、少用差的，也留一部分给新策略试。

## 和 lilto 不一样的地方

- r 类图（品牌、拿不准）lilto 直接放行，真数据里占 18%，带简体营销字的就漏了；这里再问一次，有就译。
- 水印字加描边；象寄明确没译成的可以再交（lilto 一律卡住，没有人工核清的入口）。
- 审稿在 NocoDB，批准在收件箱；建商品、上架是写入，走 `x2 propose` → 批准 → `x2 run`。
- 店铺按 Shopee 的店铺 id 认（lilto 用的是卖家账号 id，两个不一样）。
