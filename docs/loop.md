# x2 怎样推进店里的事（草稿）

读者是在 x2 里开 agent（Claude Code、Codex）推进两家店日常工作的人和 agent，和要做表、视图的人。这份讲 x2 怎么一轮一轮推进：现读站点、算出要做的事、人在收件箱里做和批准、x2 执行写入再读回来；还有为这个循环服务的表、视图和代码。订单从进来到「已打包」的细节在 [orders.md](orders.md)；每个词的意思在 [glossary.md](glossary.md)，词和它不一样的照它改。

来源：运营讲的流程（2026-10-09）；运营答过的规矩取自 lilto 的 `docs/requirements/orders.md`（2026-09-29）；站点的真实数据。同事整理的旧流程（`old-workflows.md`，W01–W33）只当线索：它的概念没有推敲过，有的自相矛盾。每个概念都先拿站点的真实数据和运营的话核对过，用得上才留。

这是草稿：没定的数字和边界在最后一节「要你们定的」。中断后接着做、换一台电脑继续、引导设置（doctor）以后再写。

## 怎样工作

**每一轮现读站点上的事实；检查算出哪里和该有的样子不一样；agent 能做的准备成待批准的写入，人要做的放进收件箱；人在收件箱里付款、批准、打包……x2 执行写入、再读回来核对。下一轮读到的事实里问题没了，收件箱里那一行自己关掉：做完 = 收件箱是空的。**

```
现读 → 检查 → agent 准备写入 / 收件箱加一行 → 人做、人批准 → x2 执行、回读 → 现读 …
```

先例：Kubernetes 的 controller（spec 和 status，按状态触发，不按事件）；lilto 的「做完 = 某个视图为空」「读取的频率是目标，不是任务」。

规矩：

1. **状态在站点和库里，不在 agent 的记忆里。** 哪台电脑开 agent，第一件事都是 `x2 status`。没有后台监听器、按钮请求、冻结范围。
2. **收件箱是算出来的，不是攒出来的。** 一件事一个 key（例 `pay:<1688 账号>`、`pack:<订单号>`），每轮重算，只更新不重复；条件不成立就自动关。只有这一行靠的那几样这一轮都读成功了，才关它：漏读不算做完。
3. **人要做的都在收件箱里，一件事一行。** 付款、批准、打包、选货源、处理问题单、登录、售后决定。收件箱在 NocoDB 里，人不用守在跑 agent 的那台电脑前。
4. **写只有一条路：agent 准备写入 → 人在收件箱批准 → 先记意图 → 提交一次 → 读回来核对。** 结果未知不重发；一个对象上有没核清的写入，先读回来，再准备新的。跑顺了的写可以配置成不用批准。
5. **只存三类：** 站点上没有的（设置、货源（带一份快照）、人报的到货问题、人的决定）；写入的记录（意图和结果）；要给团队在表里看的（订单的进度看板，每轮现读后重写，不当真相用）。站点上有的（购物车、采购单、1688 商品详情、店里的商品、登录着的账号）每轮经浏览器现读，不存。
6. **数字由代码算，文字由 agent 写，看图、译图交给外部服务。** 代码核对 agent 引用的数字；外部服务按输入复用结果，不重复收费。
7. **词从站点和运营的话来，一个概念一个词。** 订单就是 Shopee 的订单，chanboss 上同一个订单号的那张是它在 chanboss 的进度；chanboss 上的事用 chanboss 的词（待处理、预报、已打包、拣货单、问题）。不自己造词，词表在 [glossary.md](glossary.md)。

## 谁管什么

| | 在哪 | 管什么 |
|---|---|---|
| 浏览器 | 本机 | 登录态：两家 Shopee、1688、知虾、chanboss。一家店一个浏览器（Chrome 的不同用户） |
| x2 | 本机 | 读写站点（每轮现读）；检查；执行批准了的写入；调外部服务 |
| agent | 本机终端 | 准备写入（列出要加购的、要预报的、起草回复、生成商品稿）；写文字；跟人说要做什么 |
| 库 | NAS 上的 Postgres | 唯一的数据。表的结构写在 x2 的代码里，由 x2 建和改 |
| NocoDB | NAS | 收件箱；团队看进度和结果；所有要人填、选、批准的 |
| 外部服务 | 网上 | 象寄（译图）、Gemini（看图）；可选 DeepSeek（批量写字） |

NocoDB 只读写库，不碰站点；要用浏览器的事都在 x2。凭证（象寄、Gemini 的 key，库的密码）留在本机的环境变量里，不进库、不进 NocoDB。NocoDB 不显示外链的图（1688 的图还挡别站的 Referer），要显示的图由 x2 经 NocoDB 的接口按链接上传成附件。

## agent 开起来做什么

写进 `AGENTS.md`（Codex 读它；`CLAUDE.md` 用 `@AGENTS.md` 引它）：

1. `x2 status`：现读站点，跑检查，更新收件箱，说三件事：这次读到了什么（哪样没读成）、收件箱里有什么、agent 能做什么。
2. 有结果未知的写入，先读回来核清。
3. agent 能做的，按对应的 skill 准备好，写成一批待批准的写入（`x2 propose`）；收件箱里会多一行「批准：……」。
4. 告诉人去收件箱。人在那一行勾「批准」就批准整批；也可以在终端里说「批准」，agent 替人写进库。
5. `x2 run`：执行批准了的写入。每项先记意图，再提交一次，再读回来；被拒、结果未知都写下来，结果未知的停下它和依赖它的。
6. 再 `x2 status`：收件箱关掉的就是做完了；没关的说为什么。

```
$ x2 status
读到    订单 84 行 · 购物车 3 行 · 采购单 334 行（ni1206 的浏览器没连着）
收件箱  付款：1688 购物车里 2 张订单的货 ¥58.20
        批准：预报 2 张订单（海快、无单号）
        打包：2 张订单的货到齐了（红T ×3 → 订单 1 一件、订单 2 两件）
        快到期：260930DHFMNW9Q 出货期限还剩 1 天，还没打包（卡在：货还没到齐）
agent   回复：5 个会话在等回复，草稿可以写
未知    0
```

## 每件事

一个主题一节。「怎样算做完」不成立的地方，agent 去准备，或者收件箱加一行。「代码」一列：有 = x2 已经有；改 = 有但要改；新 = 要写；缺 = 站点上的写还没有做出来。

## 表

只存三类（见「怎样工作」第 5 条）。第 0、1 阶段只有这 6 张；后面几个阶段的表，照同一条规矩一张张定存不存。表名、列名在库里用英文，NocoDB 里显示中文。

| 表 | 一行是 | 主要的列 | 为什么存 |
|---|---|---|---|
| 收件箱 `inbox` | 一件要人做的事 | 类别（付款、批准、打包、选货源、规格对不上、快到期、没发货、取消、问题单、到货问题、登录、结果未知……）、事情、详情、谁做（现在都是运营）、店铺、期限、去哪做（链接）、「批准」（只有批准这一类有）、「处理好了」（x2 看不到结果的事，人做完勾）、开着 / 关了、推迟到、备注、key、开始和关掉的时间。人只改「批准」「处理好了」「推迟到」「备注」 | 人在上面勾、写；不在开着浏览器的电脑前也要能看 |
| 写入 `writes` | 做了一次写操作（改站点，或交一张图给象寄：交一次收一次钱） | 批次（对收件箱里的一行「批准」）、操作（加购、预报、取消预报、回复……）、对象、参数（JSON）、给人看的、防重复的 key、「做」（人在批准前取消勾 = 这一项不做）、状态（待批准、已批准、已提交、成功、被拒、结果未知、已核对、不一致、没做）、站点的回应、回读（做之前、做之后）、原因、在哪台电脑、开始和结束时间、费用 | 意图和结果站点上没有；防重复、核清结果未知、对采购单都靠它 |
| 货源 `sources` | 店里一个商品 × 一个货源 | 店里的商品（id、名字、图）；货源在哪个站、id；快照：链接、标题、图、规格（名字、价格、库存、图）、什么时候读的；像不像（店里卖过的规格有几成在它里面配得上）、对不上的规格、从哪来（以图搜图、人贴的链接、以前定的）、明显对得上（x2 标的：随加购一起批准）、用这个（人勾；一个商品最多一行）、用不了（用这个的货源下架了）。不存规格的对应：加购时按店里的规格名在货源的规格里配，配不上进收件箱「规格对不上」。x2 source 找到的都在这里，还没勾「用这个」的是还在挑的；重新找时还在挑的删掉 | 人的决定；快照给人挑、知道下架前是什么、比价（买之前一律现读） |
| 到货问题 `arrival_issues` | 一个到货问题 | 订单号、哪件、问题（错货、少件、坏了、其他）、几件、备注、怎么处理（退换、重新买、不用管）、处理好了 | 人报的，站点上没有 |
| 订单设置 `order_settings` | 一行 | 采购账号（1688 会员名，只往它加购）、快到期提前几天（6）、付款后几小时没发货算异常（48）、预报要不要批准、发货线路（海快：chanboss 的 sendway 752、线路 1111、仓库 5176） | 设置 |
| 订单 `orders` | 一张订单（Shopee 和 chanboss 同一个订单号） | 店铺、订单号、下单时间、出货期限、平台状态、chanboss 状态、商品、问题单；检查算出来的：剩几天、寄到哪、卡在哪一步、细节 | 给团队看进度（待出货看板）。每轮现读 chanboss 后重写 |

收件箱的 key 写成「类别:对象」，例：`pay:<1688 账号>`、`approve:<批次>`、`pack:<订单号>`、`source:<商品 id>`、`sku:<规格 id>`、`late:<订单号>`、`unshipped:<采购单号>`、`cancel:<订单号>`、`cancel-goods:<订单号>`、`issue:<编号>`、`login:<读什么>:<谁>`。写入的防重复 key 同理，例 `cart:<订单号>:<规格 id>,…`、`forecast:<订单号>`、`reply:<会话 id>:<买家最后一条消息 id>`、`xiangji:<图片内容哈希>`：同一个 key 已有成功或结果未知的写入，不再提交。

收件箱里「批准」这一类，一行是一批写入：勾一下就批准整批；要去掉几项，在「写入」里把那几行的「做」取消勾。

后面几个阶段可能要存的：选品候选、商品稿（人的决定和审稿）、报告（给团队看）、店铺参数（核价的设置）。会话、评价、售后、知虾的数据先按现读想，要看历史再存。

## 视图

NocoDB 里每张表可以有几个视图，什么事用什么样的视图。侧栏第一张放「收件箱」，默认视图是「要我做的」。每个视图写「空的时候」：空了就是这件事做完了。要人做的都在收件箱里，别的视图是给人看进度、填东西的。

| 视图 | 表 | 样子 | 筛选、排序、分组 | 空的时候 |
|---|---|---|---|---|
| 要我做的 | 收件箱 | 表格 | 开着、不在推迟中；期限从近到远，按类别分组 | 现在没有要你做的 |
| 最近关掉的 | 收件箱 | 表格 | 7 天内关掉的，新的在前 | — |
| 待出货 | 订单 | 看板 | 待出货、还没打包；按「卡在哪一步」分列，列里按出货期限排 | 没有待出货的订单 |
| 全部 | 订单 | 表格 | 下单时间，新的在前 | — |
| 报到货问题 | 到货问题 | 表单 | 订单号、哪件、问题、几件、备注、怎么处理 | — |
| 没处理好的 | 到货问题 | 表格 | 没勾「处理好了」 | 没有没处理的到货问题 |
| 选货源 | 货源 | 表格（以后画廊） | 还没勾「用这个」的，按店里的商品分组，像的在前 | 卖出的商品都有货源 |
| 定了的 | 货源 | 表格 | 勾了「用这个」的 | — |
| 全部 | 写入 | 表格 | 编号，新的在前 | — |
| 设置 | 订单设置 | 表格（点开一行改） | — | — |

以后：选品（看板）、商品稿（画廊）、报告（日历或表格），到那个阶段再定。

`x2 nocodb` 按这张表建（`src/nocodb.ts`，可以重复跑）。看板要「单选」类型的列：NocoDB 改列类型会改库里的表结构，所以只在 NocoDB 的元数据里把「卡在哪一步」标成单选（库里还是 text），取值的顺序就是看板列的顺序。NocoDB 对外部的库「改名」就是改表名、改列会重写列定义（试过：去掉了 NOT NULL），所以库在 NocoDB 里设成表结构只读，中文名直接写 NocoDB 自己的元数据库。图现在是链接，点开看；传成附件以后再做（选货源、打包用画廊）。

看板、画廊、表单是 NocoDB 免费版就有的；选中几行一起改（批量批准）也有。按钮里跑脚本要付费版，这里不需要：要跳到站点的地方放一列链接（例「去 1688 购物车」「在 chanboss 打开这张订单」）。

## 代码

### 命令

```
x2 status                现读站点 → 检查 → 更新收件箱 → 说要做什么（--json 给 agent：todo 里有现成的一批写入）
x2 propose               agent 写一批待批准的写入（JSON 从 stdin 进）；只收检查算出来该做的；收件箱加一行「批准」
x2 approve <批次>         人在终端里说「批准」：agent 替人勾上
x2 run [--try 操作]       执行批准了的写入；没在真站点上跑过的写操作，要和人约好、加 --try 才做
x2 source [商品…] [--url 链接]  给店里的商品找货源：以图搜图，看卖过的规格有几成配得上；人贴了链接就用它。不给商品就找检查算出来缺的
x2 report <店>           一家店最近完整 7 日的事实
x2 listing …            商品稿：生成、检查
x2 db migrate | import   建表、加列；把 ~/x2 的 JSON 迁进库（只用一次）
x2 nocodb                按「视图」一节建 NocoDB：连库、中文名、侧栏顺序、视图（可以重复跑）
```

### 算（`src/calc/`）

- **核价**（W11）：到岸成本 = 1688 价 × 件数 + 已知的国内运费、包材 + 计费重 × 货代每公斤 + 每单固定费，人民币按汇率换成新台币；实收 = 售价 − 佣金 − 金流费 − 其他平台费；利润 = 实收 − 到岸成本 − 风险预留；利润率 = 利润 ÷ 实收。求售价：满足「利润率 ≥ 目标、利润 ≥ 最低额」的最小整数价。缺的费用列成「未计」，不当 0。
- **广告指标**（W27）：CTR = 点击 ÷ 曝光，CPC = 花费 ÷ 点击，ROAS = 归因销售额 ÷ 花费……汇总先加原量再相除；分母是 0 或缺就留空。

### 图片（`src/service/`，W09）

商品稿的图按这个顺序，便宜的检查在前，收费的在后：

1. 收图、按内容哈希去重：货源的主图、规格图（详情图要补读）。
2. Gemini 看图：只送有字或有风险的图，一次送几张；每张回「能用、要改、不用、拿不准」，拿不准不算通过。按「图片哈希 + 提示版本」缓存。
3. 象寄译图：只送有简体字的图；每交一张记一行写入（交一次收一次钱），记下 RequestId；结果未知按 RequestId 查，不重交。
4. 水印：本地按店铺设置加字，不收费；没开水印的店不加。
5. 传图：先用这个商品已有的图；新的传 Shopee，拿到图片 id 才算。
