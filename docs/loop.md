# x2 怎样推进店里的事

读者是在 x2 里开 agent（Claude Code、Codex）推进两家店日常工作的人和 agent，和要做表、视图的人。这份讲 x2 怎么一轮一轮推进，和为这个循环服务的表、视图、代码。订单在 [orders.md](orders.md)，上品在 [listing.md](listing.md)，词在 [glossary.md](glossary.md)，agent 开起来做什么在 [AGENTS.md](../AGENTS.md)。

## 怎样工作

**每一轮现读站点上的事实；检查算出哪里和该有的样子不一样；agent 能做的准备成待批准的写入，人要做的放进收件箱；人在收件箱里付款、批准、打包……x2 执行写入、再读回来核对。下一轮读到的事实里问题没了，收件箱里那一行自己关掉：做完 = 收件箱是空的。**

```
现读 → 检查 → agent 准备写入 / 收件箱加一行 → 人做、人批准 → x2 执行、回读 → 现读 …
```

规矩：

1. **状态在站点和库里，不在 agent 的记忆里。** 哪台电脑开 agent，第一件事都是 `x2 status`。没有后台监听器。
2. **收件箱是算出来的，不是攒出来的。** 一件事一个 key（例 `pay:<1688 账号>`、`pack:<订单号>`），每轮重算，只更新不重复；条件不成立就自动关。这一行靠的那几样这一轮都读成功了，才关它：漏读不算做完。
3. **人要做的都在收件箱里，一件事一行。** 收件箱在 NocoDB 里，人不用守在跑 agent 的那台电脑前。
4. **写只有一条路：agent 准备写入 → 人在收件箱批准（商品稿：人在那一行勾「批准上架」）→ 先记意图 → 提交一次 → 读回来核对。** 结果未知不重发；一个对象上有没核清的写入，先读回来，再准备新的。跑顺了的写可以设成不用批准。
5. **只存三类：** 站点上没有的（设置、货源和它的快照、人的决定、人报的到货问题、商品稿）；写入的记录；给团队看的（订单的进度，每轮现读后重写）。站点上有的（购物车、采购单、店里的商品、登录着的账号）每轮经浏览器现读，不存。
6. **数字由代码算，文字由 agent 写，看图、译图交给外部服务。** 外部服务的结果按输入缓存，不重复收费。
7. **词从站点和运营的话来，一个概念一个词。** 词表在 [glossary.md](glossary.md)。

## 谁管什么

| | 在哪 | 管什么 |
|---|---|---|
| 浏览器 | 本机 | 登录态：两家 Shopee、1688、知虾、chanboss。一家店一个浏览器（Chrome 的不同用户）；x2 按登录选浏览器，几个 x2 同时跑时同一个浏览器的同一个站点一次一个进程 |
| x2 | 本机 | 读写站点；检查；执行批准了的写入；调外部服务 |
| agent | 本机终端 | 准备写入、写文案、跟人说要做什么 |
| 库 | Postgres（现在在本机，要搬到 NAS） | 唯一的数据。表的结构写在 x2 的代码里，由 x2 建和改 |
| NocoDB | 现在在本机，要搬到 NAS | 收件箱；团队看进度；人填、选、批准的 |
| 外部服务 | 网上 | Gemini（看图）、象寄（译图，收费） |

NocoDB 只读写库，不碰站点。凭证（库的地址，Gemini、象寄的 key）在本机的环境变量或 `.env` 里，不进库、不进 NocoDB。1688 的图挡别站的 Referer，NocoDB 显示不了；商品稿的图放的是 Shopee 的图片地址（公开的），NocoDB 直接显示。

## 每件事

一个主题一节。「怎样算做完」不成立的地方，agent 去准备，或者收件箱加一行。

- **订单**：从进来到 chanboss「已打包」，在 [orders.md](orders.md)。
- **上品**：从一个货源到一家店在售，在 [listing.md](listing.md)。

### 客服

| 事 | 怎样算做完 | 代码 | 人 |
|---|---|---|---|
| 买家消息有人回 | 没有「最后一条是买家发的、等了超过 X 小时」的会话 | 有 `conversations`、`unreplied`、`messages`；缺：发聊聊 | 批准回复；退款、赔偿、交期承诺由人定 |
| 评价有回复 | 没有没回复的评价，低星的先 | 有 `reviews`；缺：回复评价 | 批准 |

发之前重读：买家又发了新消息，原来的草稿作废。chanboss 上没到「已出库」，不说「已寄出」；不说哪天到。

### 商品维护

| 事 | 怎样算做完 | 代码 | 人 |
|---|---|---|---|
| 备货天数够 | 每个在售商品是预购，备货天数够从 1688 到 chanboss 再到台湾 | 有 `shopee product`、`updateProduct`（没接） | 批准 |
| 在售商品的货源还在 | 每个在售商品有货源；货源在售、有货、规格配得上、价格没涨过 X% | 有 `shopee products`、`1688 offer` | 换货源 |
| 每个规格赚钱 | 按现在的货源价和店铺设置核价，含进行中的折扣 | 有核价（`src/listing/price.ts`）、`updateProduct`（没接） | 批准改价 |
| 没人看的下架 | 没有「最近 30 天点击、加购都是 0」的在售商品；新品、有订单的不算 | 有 `performance`、`setUnlisted` | 批准 |
| 活动、广告不亏 | 进行中的折扣价核价不亏；投放中的商品都有货、利润已知 | 有 `discounts`、`campaigns`、`gms-items`；只提醒 | 在 Shopee 上改 |

### 选品

agent 自己定策略、做实验（explore / exploit）：选货源、上品、看效果，多用好的策略、少用差的，也留一部分试新的。x2 要做的是记下策略、跟踪效果：

| 事 | 怎样算做完 | 代码 | 人 |
|---|---|---|---|
| 每份商品稿知道从哪个策略来 | 商品稿的「策略」有值 | 有（`x2 listing add --strategy`） | — |
| 回头查为什么选 | 按策略选的商品稿有选品理由、依据、选品快照（当时的策略版本、在用的选品规矩）；策略每一版有变更记录 | 有（`x2 listing add --why`、`x2 listing why`、`x2 strategy set --why`、`x2 rule`） | — |
| 按策略看效果 | 每个策略上出来的商品的曝光、点击、加购、订单、毛利 | 有 `shopee performance`、知虾的读、策略表；缺：按策略汇总 | 看实验结果 |

### 经营分析

| 事 | 怎样算做完 | 代码 | 人 |
|---|---|---|---|
| 每周每店一份报告 | 每家店有最近完整 7 天的报告 | 有 `shop-metrics`、`performance`；缺：`x2 report` 算事实，agent 写说明 | 看；把建议转成要做的事 |
| 店铺没有新处罚 | — | 缺读接口（健康分、处罚） | 人看 |

广告指标：CTR = 点击 ÷ 曝光，CPC = 花费 ÷ 点击，ROAS = 归因销售额 ÷ 花费；汇总先加原量再相除，分母是 0 或缺就留空。

## 表

表名、列名在库里用英文，NocoDB 里显示中文。结构在 `src/db/schema.sql`。

| 表 | 一行是 | 为什么存 |
|---|---|---|
| 收件箱 `inbox` | 一件要人做的事（人只改「批准」「已处理」「推迟至」「备注」） | 人在上面勾、写 |
| 写入 `writes` | 一次写操作：批次、操作、参数、防重复的 key、「执行」、状态（待批准、已批准、已提交、成功、被拒、结果未知、已核对、不一致、未执行）、站点响应、回读 | 意图和结果站点上没有；防重复、核清结果未知、采购单分给订单都靠它 |
| 货源 `sources` | 店里一个商品 × 一个货源：快照、相似度、选用、不可用、规格例外 | 人的决定；快照给人挑、比价 |
| 到货问题 `arrival_issues` | 一个到货问题 | 人报的 |
| 订单设置 `order_settings` | 一行：采购账号、快到期提醒（天）、未发货提醒（付款后小时数）、预报要批准、发货线路 | 设置 |
| 订单 `orders` | 一张订单，加上检查算出来的剩余天数、当前步骤 | 给团队看进度；每轮现读后重写 |
| 店铺设置 `shop_settings` | 一家店：核价参数、上品的默认值、允许的类目、水印、暂停上品 | 设置 |
| 商品稿 `listings` | 一个货源 × 一家店；选品理由、依据、选品快照；批准上架（勾的时候内容的 hash）、备注 | 人的决定和审稿；建商品要的内容；回头查为什么选 |
| 策略 `strategies`、策略变更记录 `strategy_changes` | 一个选品策略（版本号）；它的一版（改之前、改之后、理由） | agent 的决定；回头查按的是哪一版 |
| 选品规矩 `selection_rules` | 一条所有策略共用的选品规矩（开始时间、结束时间、停用原因） | agent 的决定；停用的不删 |
| 图 `images`、`shop_images` | 一张图（字节的 sha256）：筛字结果、译图的字节；传到哪家店、图片 id | 不重复付钱、不重复传（NocoDB 里不显示） |

收件箱的 key 是「类别:对象」，例 `pay:<1688 账号>`、`approve:<批次>`、`pack:<订单号>`、`source:<商品 id>`、`sku:<规格 id>`、`late:<订单号>`、`unshipped:<采购单号>`、`cancel:<订单号>`、`cancel-goods:<订单号>`、`issue:<编号>`、`listing-fix:<商品稿>`、`listing-approve:<店>`、`login:<读什么>:<谁>`。写入的防重复 key 同理，例 `cart:<订单号>:<规格 id>,…`、`forecast:<订单号>`、`xiangji:<图的 sha256…>`、`create:<店>:<货号>`：同一个 key 已有成功或结果未知的写入，不再提交。

收件箱里「批准」这一类，一行是一批写入：勾一下就批准整批；要去掉几项，在「写入」里取消那几行的「执行」。商品稿不在收件箱里批准：收件箱一家店一行「待批准：N 个商品稿」，人到「商品稿」里一份一份勾「批准上架」，`x2 run` 照勾生成建商品、上架的写入；没有待批准的就关。

## 视图

侧栏第一张是「收件箱」，视图「待处理」。要人做的都在收件箱里，别的表给人看进度、填东西、勾批准上架。一张表一个表格视图（到货问题、商品稿另有一个表单）；「空的时候」就是这件事做完了。

| 表 | 视图 | 样子 | 筛选、分组、排序 | 空的时候 |
|---|---|---|---|---|
| 收件箱 | 待处理 | 表格 | 未关闭、不在推迟中；按类别分组，期限从近到远 | 没有要你做的 |
| 订单 | 全部 | 表格 | 按当前步骤分组；出货期限从近到远 | — |
| 到货问题 | 全部 | 表格 | 没勾「已处理」的在前，上报时间新的在前 | — |
| 到货问题 | 上报到货问题 | 表单 | — | — |
| 商品稿 | 全部 | 表格，行高「高」，主图、规格图、详情图是缩略图 | 按当前步骤分组：待批准、待补充在最前，已上架、已放弃在最后；组里按编号。第一列简称，接着批准上架、当前步骤、说明、备注 | — |
| 商品稿 | 添加货源 | 表单 | — | — |
| 策略、策略变更记录、选品规矩 | 全部 | 表格 | 策略：创建时间，新的在前；变更记录：变更时间，新的在前；规矩：编号 | — |
| 货源 | 全部 | 表格 | 按店里的商品分组，选用的在前、相似度高的在前；一组里没勾「选用」的就是还没选 | — |
| 写入 | 全部 | 表格 | 编号，新的在前 | — |
| 订单设置、店铺设置 | 设置 | 表格 | — | — |

图（`images`、`shop_images`）在 NocoDB 里藏起来（标成多对多的中间表，NocoDB 默认不显示），库里照旧。

`x2 nocodb` 按这张表建（`src/nocodb.ts`，可以重复跑：多出来的视图删掉）。NocoDB 按值排组，单选不按取值的顺序：商品稿按当前步骤倒序分组（`step` 按字的编码排，倒序正好是待补充、待批准在最前，已批准、已上架在最后）。给 NocoDB 看的列不用 enum：NocoDB 拿单选列和空字符串比，enum 不收，整张表读不出来。NocoDB 对外部的库改名就是改表名、改列会重写列定义，所以库在 NocoDB 里设成表结构只读：中文名、单选（看板的列）、链接、附件、显示值都只写 NocoDB 自己的元数据库，库里的表结构只由 `schema.sql` 改。

## 命令

```
x2 status                现读站点 → 检查 → 更新收件箱 → 说要做什么（--json：todo 里有现成的一批写入）
x2 propose               agent 写一批待批准的写入（JSON 从 stdin 进）；收件箱加一行「批准」
x2 approve <批次>         人在终端里说「批准」：agent 替人勾上
x2 run [--try 操作,…]     执行批准了的写入（勾了「批准上架」、内容没变的商品稿先生成建商品、上架）；没在真站点跑过的写操作要加 --try；执行完马上重算涉及的商品稿的当前步骤（收件箱等 x2 status）
x2 source …              给商品找货源、写规格例外
x2 listing …             上品：quote、add、why、make、estimate、show、text、audit、keep、drop、approve、noted、list
x2 strategy …            选品的策略：add、set、list、log
x2 rule …                选品规矩：add、retire、list
x2 <站点> <操作>          读站点（只读）
x2 db migrate | import | import-shops
x2 nocodb                建 NocoDB 的中文名和视图
```

目录在 [README](../README.md)。

## 站点上还缺的

- chanboss：预报没在真订单上跑过；取消预报没做（页面的请求走另一个后端，地址没核实）。
- Shopee：改价、改库存、改内容（`updateProduct`）、改折扣（`updateDiscountItems`）有函数、没接；发聊聊、回评价、售后同意和拒绝没有；健康分和处罚读不了。
- 1688：阶梯价、包装重量读不了；`1688 search` 卡片上没有起订量时 `minQty` 是 0，应该是空。

## 顺序

| 阶段 | 进 x2 的 | 人做的 | 做完的标准 |
|---|---|---|---|
| 0 地基 | 库、现读、检查、写入；`x2 status` / `propose` / `approve` / `run`；按店找浏览器；收件箱、写入 | 在收件箱里做事、批准 | 任何一台电脑开 agent，`x2 status` 说得出两家店现在要做什么，和 NocoDB 收件箱一样 |
| 1 订单 | 订单、购物车、采购单现读；选货源；采购单分给订单；加购、预报；快到期、未发货、买家取消、问题单、到货问题 | 批准加购和预报；付款；打包；选货源；上报到货问题 | 运营连续一周只用 x2 和 NocoDB 处理订单，没有一张订单过期取消 |
| 2 客服和售后 | 会话、评价、售后、退件；发聊聊、回评价、售后同意和拒绝 | 批准回复；售后决定 | 没有等回复超过 X 小时的会话 |
| 3 商品维护 | 备货天数、货源还在不在、核价；改价、改库存、下架 | 批准改动、换货源 | 在售的商品备货天数都够、货源都在、利润达标 |
| 4 上品和选品 | 商品稿、建商品、上架；策略、按策略看效果 | 贴货源、审稿、批准 | 一个货源从贴进来到在售，中间只有人审稿和批准 |
| 5 经营分析和结算 | `x2 report`、收入核对 | 看报告 | 每家店每周一份报告，数都对得到表里的行 |

## 要定的

1. **阈值**：买家等多久算该回；几星以下的评价要处理；货源涨价多少算不对；备货天数至少几天。
2. **核价参数**：店铺设置里的值要运营核一遍还对不对。
3. **售后**：运营要在系统里同意、拒绝，要先把这个写做出来；之前由人在 Shopee 上做，x2 在收件箱提醒。
4. **NAS**：极空间，局域网里直接连。在外面怎么连（例 Tailscale）还要定。
