# x2 怎样推进店里的事（草稿）

读者是在 x2 里开 agent（Claude Code、Codex）推进两家店日常工作的人和 agent，和要做表、视图的人。这份讲 x2 怎么一轮一轮推进：同步站点、算出要做的事、人在收件箱里做和批准、x2 执行写入再读回来；还有为这个循环服务的表、视图和代码。订单从进来到「已打包」的细节在 [orders.md](orders.md)；每个词的意思在 [glossary.md](glossary.md)，词和它不一样的照它改。

来源：运营讲的流程（2026-10-09）；运营答过的规矩取自 lilto 的 `docs/requirements/orders.md`（2026-09-29）；站点的真实数据。同事整理的旧流程（`old-workflows.md`，W01–W33）只当线索：它的概念没有推敲过，有的自相矛盾。每个概念都先拿站点的真实数据和运营的话核对过，用得上才留。

这是草稿：没定的数字和边界在最后一节「要你们定的」。中断后接着做、换一台电脑继续、引导设置（doctor）以后再写。

## 怎样工作

**站点上的事实同步进库；检查算出哪里和该有的样子不一样；agent 能做的准备成待批准的写入，人要做的放进收件箱；人在收件箱里付款、批准、打包……x2 执行写入、再读回来核对。下一轮同步来的事实里问题没了，收件箱里那一行自己关掉：做完 = 收件箱是空的。**

```
同步 → 检查 → agent 准备写入 / 收件箱加一行 → 人做、人批准 → x2 执行、回读 → 同步 …
```

先例：Kubernetes 的 controller（spec 和 status，按状态触发，不按事件）；lilto 的「做完 = 某个视图为空」「读取的频率是目标，不是任务」。

规矩：

1. **状态在站点和库里，不在 agent 的记忆里。** 哪台电脑开 agent，第一件事都是 `x2 status`。没有后台监听器、按钮请求、冻结范围。
2. **收件箱是算出来的，不是攒出来的。** 一件事一个 key（例 `pay:<1688 账号>`、`pack:<订单号>`），每轮重算，只更新不重复；条件不成立就自动关。只有这一域这一轮同步完整了，才关它的那几行：漏读不算做完。
3. **人要做的都在收件箱里，一件事一行。** 付款、批准、打包、选货源、处理问题单、登录、售后决定。收件箱在 NocoDB 里，人不用守在跑 agent 的那台电脑前。
4. **写只有一条路：agent 准备写入 → 人在收件箱批准 → 先记意图 → 提交一次 → 读回来核对。** 结果未知不重发；一个对象上有没核清的写入，先读回来，再准备新的。跑顺了的写可以配置成不用批准。
5. **只存三类：** 站点上没有的（规则、货源、人的决定）；写入的记录（意图和结果）；要看历史、要给团队在表里看的（站点数据的镜像）。写之前一律现读，不信镜像。
6. **数字由代码算，文字由 agent 写，看图、译图交给外部服务。** 代码核对 agent 引用的数字；外部服务按输入复用结果，不重复收费。
7. **词从站点和运营的话来，一个概念一个词。** 订单就是 Shopee 的订单，chanboss 上同一个订单号的那张是它在 chanboss 的进度；chanboss 上的事用 chanboss 的词（待处理、预报、已打包、拣货单、问题）。不自己造词，词表在 [glossary.md](glossary.md)。

## 谁管什么

| | 在哪 | 管什么 |
|---|---|---|
| 浏览器 | 本机 | 登录态：两家 Shopee、1688、知虾、chanboss。一家店一个浏览器（Chrome 的不同用户） |
| x2 | 本机 | 读写站点；同步；检查；执行批准了的写入；调外部服务 |
| agent | 本机终端 | 准备写入（列出要加购的、要预报的、起草回复、生成商品稿）；写文字；跟人说要做什么 |
| 库 | NAS 上的 Postgres | 唯一的数据。表的结构写在 x2 的代码里，由 x2 建和改 |
| NocoDB | NAS | 收件箱；团队看进度和结果；所有要人填、选、批准的 |
| 外部服务 | 网上 | 象寄（译图）、Gemini（看图）；可选 DeepSeek（批量写字） |

NocoDB 只读写库，不碰站点；要用浏览器的事都在 x2。凭证（象寄、Gemini 的 key，库的密码）留在本机的环境变量里，不进库、不进 NocoDB。NocoDB 不显示外链的图（1688 的图还挡别站的 Referer），要显示的图由 x2 经 NocoDB 的接口按链接上传成附件。

## agent 开起来做什么

写进 `AGENTS.md`（Codex 读它；`CLAUDE.md` 用 `@AGENTS.md` 引它）：

1. `x2 status`：同步过期的数据，跑检查，更新收件箱，说三件事：数据新不新、收件箱里有什么、agent 能做什么。
2. 有结果未知的写入，先读回来核清。
3. agent 能做的，按对应的 skill 准备好，写成一批待批准的写入（`x2 propose`）；收件箱里会多一行「批准：……」。
4. 告诉人去收件箱。人在那一行勾「批准」就批准整批；也可以在终端里说「批准」，agent 替人写进库。
5. `x2 run`：执行批准了的写入。每项先记意图，再提交一次，再读回来；被拒、结果未知都写下来，结果未知的停下它和依赖它的。
6. 再 `x2 status`：收件箱关掉的就是做完了；没关的说为什么。

```
$ x2 status
数据    chanboss 3 分钟前 · 购物车 5 分钟前 · 采购单 20 分钟前 · 聊聊 8 分钟前
收件箱  付款：1688 购物车里 2 张订单的货 ¥58.20
        批准：预报 2 张订单（海快、无单号）
        打包：2 张订单的货到齐了（红T ×3 → 订单 1 一件、订单 2 两件）
        快到期：260930DHFMNW9Q 出货期限还剩 1 天，还没打包（卡在：货还没到齐）
agent   回复：5 个会话在等回复，草稿可以写
未知    0
```

## 每件事

一个主题一节。「怎样算做完」不成立的地方，agent 去准备，或者收件箱加一行。「代码」一列：有 = x2 已经有；改 = 有但要改；新 = 要写；缺 = 站点上的写还没有做出来。

### 订单

订单从进来到 chanboss「已打包」，以后加上售后、退件、结算：在 [orders.md](orders.md)。

### 客服（W22、W23）

| 事 | 怎样算做完 | 代码 | 人 |
|---|---|---|---|
| 买家消息有人回 | 没有「最后一条是买家发的、等了超过 X 小时」的会话 | 有 `conversations`、`unreplied`、`messages`；新：同步、取上下文（订单、chanboss 状态）；缺：发聊聊 | 批准回复（收件箱）；退款、赔偿、交期承诺由人定 |
| 评价有回复 | 没有没回复的评价，低星的先 | 有 `reviews`；缺：回复评价 | 批准（收件箱） |

发之前重读：买家又发了新消息，原来的草稿作废、重写。chanboss 上没到「已出库」，不说「已寄出」；不说哪天到。

## 表

三类：人填的设置和决定；同步来的镜像（人只看，下一轮会覆盖）；收件箱、写入和同步（x2 写，人勾、写备注）。表名、列名在库里用英文，NocoDB 里显示中文。★ = 第一阶段（订单）就要。

### 设置和决定（人在 NocoDB 里填）

| 表 | 一行是 | 主要的列 |
|---|---|---|
| ★ 店铺 `shops` | 一家店 | 账号名（ni1206、cheeroutdoor）、店名、平台店铺 id、账号 id、浏览器、启用；店铺参数：目标利润率、最低利润额、汇率、货代每公斤、计重步长、每单固定费、平台费率、风险预留；水印开关和文字 |
| ★ 订单设置 `order_settings` | 一行 | 发货线路（海快：chanboss 的 sendway 752、线路 1111、仓库 5176）、chanboss 的收货地址、预报要不要批准、快到期提前几天（先填 2） |
| ★ 货源候选 `source_options` | 一个规格的一个候选（货源 + 1688 规格） | 两边的图、名字、价格、库存、像不像、从哪来（这个商品用过的、以图搜图、人贴的链接）、明显对得上（x2 标的：随加购一起批准）、「用这个」（人勾）。x2 写候选，人勾；勾了下一轮写进规格的货源 |
| 选品候选 `candidates` | 一个产品方向 | 用途、类目、证据（文字和链接）、找货词、状态（新、研究中、要做、不做、已上架）、理由 |

### 镜像（同步来的，人只看）

| 表 | 一行是 | 主要的列 |
|---|---|---|
| ★ 订单 `orders` | 一张订单（Shopee 和 chanboss 同一个订单号） | 店铺、订单号、下单时间、出货期限、平台状态、chanboss 状态（待处理、已预报、已到齐、已打包、已出库……）、商品（JSON：规格 id、名字、规格、件数、图；NocoDB 里显示成一段文字）、问题单；算出来的：剩几天、货源齐没齐、加购、付款、货到齐没、卡在哪一步 |
| ★ 规格 `skus` | 店里的一个规格 | 店铺、商品 id、规格 id、商品名、规格名、图、价、库存、状态、预购和备货天数、7 日和 30 日表现；**人定的两列**：货源、1688 规格（选货源以后写，同步不改）；算出来的：成本、利润率 |
| ★ 购物车 `cart` | 1688 购物车的一行 | 1688 账号、货源、1688 规格、件数、属于哪几张订单（按加购的写入）、该不该买（那几张订单还要不要发） |

| ★ 货源 `offers` | 1688 上的一个商品 | 标题、图、价格区间、起订量、单位、1688 规格（JSON：规格 id、名字、图、价、库存）、在售 / 下架、读到时间 |
| 退件 `returns_stock` | chanboss 的一条退件 | 规格、件数、状态（在架、分拣中……） |

| 会话 `conversations` | 一个聊聊会话 | 店铺、会话 id、买家、最后一条（谁发的、内容、时间）、等了多久、订单号 |
| 评价 `reviews` | 一条评价 | 店铺、评价 id、星级、内容、商品、订单号、有没有回复 |
| 店铺日数据 `shop_days` | 店铺 × 天 | 成交额、订单、访客、转化、广告花费 |
| 市场词 `market_words` | 类目 × 词 | 搜索量、30 日销量、商品数、均价、竞争、读到时间 |
| 收入 `income` | 一张已拨款的订单 | 订单号、拨款日、净额、组成（JSON） |

### 收件箱、写入和同步（x2 写，人勾、写备注）

| 表 | 一行是 | 主要的列 |
|---|---|---|
| ★ 收件箱 `inbox` | 一件要人做的事 | 类别（付款、批准、打包、选货源、快到期、取消、问题单、登录、结果未知、设置、售后……）、标题、详情、店铺、期限、去哪做（链接）、「批准」（只有批准这一类有）、开着 / 关了、推迟到、备注、key、开始和关掉的时间。人只改「批准」「推迟到」「备注」 |
| ★ 写入 `writes` | 做了一次写操作（改站点，或交一张图给象寄：交一次收一次钱） | 批次（对收件箱里的一行「批准」）、操作（加购、预报、取消预报、回复……）、对象、参数（JSON）、给人看的（旧值 → 新值）、防重复的 key、「做」（人在批准前取消勾 = 这一项不做）、状态（待批准、已批准、已提交、成功、被拒、结果未知、已核对、不一致、没做）、站点的回应、回读（做之前、做之后）、原因、在哪台电脑、开始和结束时间、费用 |
| ★ 同步 `syncs` | 一样要同步的东西 | 读什么、哪家店铺或参数、目标多新、上次读到、上次结果（成功、部分、失败和原因）、行数、在哪台电脑。知虾要读的类目和词也是这里的行，人可以加 |
| 报告 `reports` | 一家店一个期间的报告 | 店铺、期间、正文、事实（JSON）、生成时间 |
| 商品稿 `listings` | 一个选品候选在一家店的稿 | 选品候选、店铺、标题、描述、类目、属性、渠道、备货天数、图片（附件）、规格（JSON：名字、价、库存、货源、成本、重量）、检查结果、状态（草稿、待审、已批准、已建、已上架、异常）、商品 id |

收件箱的 key 写成「类别:对象」，例：`pay:<1688 账号>`、`approve:<批次>`、`pack:<订单号>`、`source:<规格 id>`、`late:<订单号>`、`cancel:<订单号>`、`problem:<订单号>`、`login:chanboss`。写入的防重复 key 同理，例 `cart:<订单号>:<规格 id>`、`forecast:<订单号>`、`reply:<会话 id>:<买家最后一条消息 id>`、`xiangji:<图片内容哈希>`：同一个 key 已有成功或结果未知的写入，不再提交。

收件箱里「批准」这一类，一行是一批写入：勾一下就批准整批；要去掉几项，点进去在写入里取消勾。

## 视图

NocoDB 里每张表可以有几个视图。侧栏第一张放「收件箱」，默认视图是「要我做的」。每个视图写「空的时候」：空了就是这件事做完了。

| 视图 | 表 | 筛选 | 排序、分组 | 空的时候 |
|---|---|---|---|---|
| 要我做的 | 收件箱 | 开着、不在推迟中 | 期限从近到远，按类别分组 | 现在没有要你做的 |
| 最近关掉的 | 收件箱 | 7 天内关掉的 | 关掉的时间，新的在前 | — |
| 结果未知 | 写入 | 结果未知 | 时间 | 没有结果未知的写入 |
| 数据新不新 | 同步 | 全部 | 落后最多的在前 | — |
| 待出货 | 订单 | 待出货、还没打包 | 按 chanboss 状态分组，组里按出货期限排 | 没有待出货的订单 |
| 快到期 | 订单 | 剩 ≤ N 天、还没打包 | 出货期限；列：订单号、店铺、剩几天、卡在哪一步 | 没有快到期的订单 |
| 选货源 | 货源候选 | 全部（规格的货源定了，检查就删掉它的候选） | 按规格分组，像的在前 | 卖出的规格都有货源 |
| 购物车 | 购物车 | 全部 | 按「该不该买」分组 | — |
| 在路上 | 采购单 | 已付款、还没签收 | 付款时间 | — |
| 售后待处理 | 售后 | 没结束 | 期限 | 没有要处理的售后 |
| 可用退件 | 退件 | 在架 | — | — |
| 等我回复 | 会话 | 最后一条是买家发的 | 等得最久的在前，按店铺分组 | 没有在等回复的买家 |
| 待回复评价 | 评价 | 没有回复 | 星级从低到高 | — |

`x2 nocodb` 按这张表建（`src/nocodb.ts`，可以重复跑）；现在建了收件箱、订单、货源候选、购物车、采购单、写入、同步、规格、货源、店铺、订单设置的视图，后面几个阶段的表有了再加。看板要「单选」类型的列，NocoDB 改列类型会改库里的表结构，所以「待出货」用分组代替看板。NocoDB 对外部的库「改名」就是改表名、改列会重写列定义（试过：去掉了 NOT NULL），所以库在 NocoDB 里设成表结构只读，中文名直接写 NocoDB 自己的元数据库。图现在是链接，点开看；传成附件以后再做。

看板、画廊、表单是 NocoDB 免费版就有的；选中几行一起改（批量批准）也有。按钮里跑脚本要付费版，这里不需要：要跳到站点的地方放一列链接（例「去 1688 购物车」「在 chanboss 打开这张订单」）。

## 代码

### 命令

```
x2 status [--no-sync]    同步过期的数据 → 检查 → 更新收件箱 → 说要做什么（--json 给 agent：todo 里有现成的一批写入）
x2 sync [域] [--shop 店]  同步：把站点读进库；不给域就同步所有过期的
x2 propose               agent 写一批待批准的写入（JSON 从 stdin 进）；只收检查算出来该做的；收件箱加一行「批准」
x2 approve <批次>         人在终端里说「批准」：agent 替人勾上
x2 run [--try 操作]       执行批准了的写入；没在真站点上跑过的写操作，要和人约好、加 --try 才做
x2 source <规格>          给一个规格找货源：这个商品用过的 → 以图搜图 → 按规格名打分
x2 report <店>           一家店最近完整 7 日的事实
x2 listing …            商品稿：生成、检查
x2 db migrate | import   建表、加列；把 ~/x2 的 JSON 迁进库（只用一次）
x2 nocodb                按「视图」一节建 NocoDB：连库、中文名、侧栏顺序、视图（可以重复跑）
```

现在的 `x2 buy` 在做第一阶段时拆掉：`x2 buy order` → `x2 sync`；`x2 buy`（要买什么的清单）→ `x2 status` 和 NocoDB 的视图；`x2 buy cart` → 加购这个写操作，经 `x2 propose`、`x2 run`；`x2 buy source` → `x2 source`。

### 算（`src/calc/`）

- **核价**（W11）：到岸成本 = 1688 价 × 件数 + 已知的国内运费、包材 + 计费重 × 货代每公斤 + 每单固定费，人民币按汇率换成新台币；实收 = 售价 − 佣金 − 金流费 − 其他平台费；利润 = 实收 − 到岸成本 − 风险预留；利润率 = 利润 ÷ 实收。求售价：满足「利润率 ≥ 目标、利润 ≥ 最低额」的最小整数价。缺的费用列成「未计」，不当 0。
- **广告指标**（W27）：CTR = 点击 ÷ 曝光，CPC = 花费 ÷ 点击，ROAS = 归因销售额 ÷ 花费……汇总先加原量再相除；分母是 0 或缺就留空。

### 图片（`src/service/`，W09）

商品稿的图按这个顺序，便宜的检查在前，收费的在后：

1. 收图、按内容哈希去重：货源的主图、规格图（详情图要补读）。
2. Gemini 看图：只送有字或有风险的图，一次送几张；每张回「能用、要改、不用、拿不准」，拿不准不算通过。按「图片哈希 + 提示版本」缓存。
3. 象寄译图：只送有简体字的图；每交一张记一行写入（交一次收一次钱），记下 RequestId；结果未知按 RequestId 查，不重交。
4. 水印：本地按店铺设置加字，不收费；没开水印的店不加。
5. 传图：先用这个商品已有的图；新的传 Shopee，拿到图片 id 才算。

## 要你们定的

1. **阈值**：快到期提前几天；买家等多久算该回；几星以下的评价要处理；货源涨价多少算不对；备货天数至少几天。
2. **店铺参数**：目标利润率、最低利润额、汇率、货代每公斤、每单固定费、平台费率，每家店各填一份（旧说明里是汇率 4.4、利润率 25%、NT$35 提醒，要核实还对不对）。
3. **文字谁写**：agent 在会话里写（建议：不用另配 key，看得到上下文，人反正要审），还是接 DeepSeek。
4. **售后**：运营要在系统里同意、拒绝。要先把这个写做出来；之前由人在 Shopee 上做，x2 在收件箱提醒。
5. **外部服务**：象寄的账号和单价；Gemini 的 key。
6. **NAS**：极空间（ZSpace），局域网里直接连（192.168.31.89）。内存够不够跑 Postgres + NocoDB（大约 1–2 GB）、在外面怎么连（例 Tailscale）还要定。现在 NocoDB 先在本机试：npm 包 `nocodb`（Node 22），元数据在本机 Postgres 的 `nocodb` 库。
